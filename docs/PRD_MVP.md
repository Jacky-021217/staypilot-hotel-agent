# StayPilot — 产品需求简表（MVP）

## 1. 背景与目标
酒店住客需求往往以自然语言描述，前台需要将信息转写为工单并判断处理部门。本项目以虚构酒店和模拟数据演示“咨询自助回答、服务任务结构化、异常转人工”流程。

## 2. 用户角色
- 酒店住客：咨询政策、提出服务请求、投诉。
- 酒店前台：接受需人工确认的请求、查看工单状态。
- 客房/工程/主管：处理对应任务（本 MVP 使用接口模拟，不连接真实人员）。

## 3. 需求优先级
| 需求 | 优先级 | MVP 验收标准 |
|---|---|---|
| 政策问答 | P0 | 能回答知识库内的信息；库外问题拒答/转人工 |
| 意图分类 | P0 | 咨询/服务请求/投诉/紧急情况分流 |
| 参数提取 | P0 | 提取房号、类型、描述、数量、语言；缺失则追问 |
| 创建工单 | P0 | 明确确认后 HTTP 调用成功，返回后端真实 ID；失败不得称成功 |
| 状态查询 | P1 | 后端可根据真实工单 ID 查询状态 |
| 业务异常 | P1 | 紧急风险提示人工；重复提交可识别 |
| 中英双语 | P1 | 中英文输入均按相同逻辑处理 |
| 真实 PMS/SaaS 集成 | 暂不做 | 仅接口模拟，不对接真实酒店数据 |

## 4. 核心流程
消息 → 分类 → [政策查询 / 服务请求 / 投诉升级 / 安全紧急事件]。
服务请求 → 提取参数 → 校验 → 获得明确确认 → POST /tickets → 返回编号或失败提示。

## 5. 约束
- 不展示真实住客个人信息或支付信息；所有资料使用合成数据。
- 工单写入接口必须校验 X-API-Key；不得将密钥硬编码在前端/GitHub。
- 不允许 AI 自主退款/改预订/保证延迟退房。
- 升级流程与多轮确认需要通过 Chatflow 会话状态变量或 Human Input 节点实现，不得仅靠“是的”一句话直接创建工单。

## 6. 需测指标
- 意图分类准确率 = 正确分类样本数 / 总分类样本数
- 工单字段完整率 = 各预期字段均提取正确的工单样本数 / 需创建工单样本数
- 未确认创建率 = 未经确认却创建的工单数 / 未确认工单场景数（目标 0）
- 工单成功率 = 真实 API 成功返回 ID 的已确认请求数 / 有效已确认请求数
- 事实准确率 = 有政策依据且信息正确的回答数 / 政策问答总数
- 异常可恢复率 = 正确提示、追问或转人工的异常数 / 异常样本总数

## 7. 范围界定
单个虚构酒店、单租户模拟、无真实库存/入住记录/酒店管理后台权限。后续可扩展 hotel_id 隔离、前台身份授权、任务 SLA 和多租户知识库过滤。
