# StayPilot 工单 API：接口设计和状态规则

酒店、房号、政策均为虚构；这只是单酒店教学用的模拟工单系统，不连接真实酒店。

## 接口一览

| Method | Endpoint | 作用 | 鉴权 |
|---|---|---|---|
| GET | `/health` | 健康检查 | 不要求 API key |
| POST | `/tickets` | 经住客确认后创建工单 | Header `X-API-Key` |
| GET | `/tickets` | 查询最近工单列表（可选 `limit`） | Header `X-API-Key` |
| GET | `/tickets/{ticket_id}` | 查询工单详情 | Header `X-API-Key` |
| PATCH | `/tickets/{ticket_id}` | 改变工单状态 | Header `X-API-Key` |

## POST `/tickets` 请求示例

```json
{
  "request_id": "my-demo-request-0001",
  "room_number": "1208",
  "category": "maintenance",
  "summary": "空调不能制冷",
  "quantity": 1,
  "priority": "normal",
  "confirmed": true
}
```

`request_id`：唯一请求标识，相同 ID 重试时返回既有工单；不同 request_id 即使内容相同也会创建新工单。
`room_number`：2–8 位大小写英文字母、数字或连字符。`category` 可选 `housekeeping`、`maintenance`、`complaint`，其中 `complaint` 虽为 API 层可用枚举，但本版 Chatflow 仍将投诉分流人工，不自动提交。`summary` 长度 3–500 字符。`quantity` 在 1–20 之间。`priority` 可选 `normal`、`high`。

`confirmed=true` 必须由 **Dify Human Input 确认通过后**构建，不能直接根据模型输出决定是否已确认。注意，这只是演示应用层约束，不构成真实身份认证与不可抵赖的审批证据。

## 响应与错误

成功：HTTP `201`，返回 `ticket_id`、`status`、`department` 等字段；重复请求也返回同一工单（MVP 中仍返回 201）。
- HTTP 400：用户未确认。
- HTTP 401：缺少或错误的 API Key。
- HTTP 404：工单不存在。
- HTTP 409：非法状态跳转。
- HTTP 422：参数校验失败，检查 FastAPI 的 `detail`。
- 网络超时或 5xx：无法确认请求是否已经生效；**不要**立刻换新的 `request_id` 重试，避免重复工单。应使用相同 `request_id` 重试或由人工核对后处理。

## 工单状态机

```text
open ──→ accepted ──→ in_progress ──→ completed
   │          │
   └──→ cancelled ←──┘
```

- `open` → `accepted` 或 `cancelled`
- `accepted` → `in_progress` 或 `cancelled`
- `in_progress` → `completed`
- `completed`、`cancelled` 为终态；不允许继续流转。

## 安全边界

仅提供共享演示 API Key，而非逐个住客身份认证，亦无真实酒店员工角色、授权审计、加密静态数据、请求限流或租户隔离。不要用真实住客姓名/房号组合、支付数据或真实酒店数据。公开的 API docs 页面会暴露接口形状，但实际敏感接口仍需 API Key。演示结束后可以关闭部署并轮换密钥。
