# StayPilot｜从 0 到 1 搭建酒店 AI 服务 Agent（MVP）

**定位：** 酒店 AI 产品经理求职作品；所有酒店政策与工单数据均为模拟数据，不连接真实酒店 PMS 系统。

## 0. 最终功能与架构
- 住客端：Dify Chatflow 的 Web App；中文和英文输入。
- 服务政策咨询：意图分类 → 知识库检索 → DeepSeek 回答。
- 房间服务/维修：意图分类 → 字段提取 → 规则校验 → Human Input 明确同意 → HTTP API → SQLite 工单保存 → 返回真实工单编号。
- 投诉/安全紧急场景：人工联系建议，**不能**假称已经联系员工或完成赔偿。
- 后端：FastAPI，演示 `POST /tickets`、`GET /tickets`、`GET /tickets/{id}`、`PATCH /tickets/{id}`。

## 1. 账户与软件
1. 注册 https://cloud.dify.ai/；进入工作区。
2. 注册 https://platform.deepseek.com/ ；建立单独的 DeepSeek API Key（按实际计费）。
3. 安装 Python 3.11/3.12、VS Code、Git；准备 GitHub 和 https://render.com/ 账号。
4. 下载并解压本项目，VS Code `File > Open Folder` 选择项目根目录。

## 2. 本地启动 FastAPI（Windows PowerShell）
从项目根目录执行：

```powershell
cd backend
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
$env:STAYPILOT_API_KEY="YOUR_RANDOM_LONG_SECRET"
python -m uvicorn app:app --reload --port 8000
```

如无 3.11，可使用 3.12；若 PowerShell 阻止激活，运行 `.\.venv\Scripts\python.exe -m pip install -r requirements.txt` 和 `.\.venv\Scripts\python.exe -m uvicorn app:app --reload --port 8000`。

浏览器查看：http://127.0.0.1:8000/health 和 http://127.0.0.1:8000/docs 。

**新开 PowerShell 终端**，设置相同密钥，测试创建：

```powershell
$env:STAYPILOT_API_KEY="YOUR_RANDOM_LONG_SECRET"
$headers=@{ "X-API-Key"=$env:STAYPILOT_API_KEY }
$body=@{
  request_id="demo-req-001"
  room_number="1208"
  category="maintenance"
  summary="空调无法制冷"
  quantity=1
  priority="normal"
  confirmed=$true
} | ConvertTo-Json
Invoke-RestMethod -Uri http://127.0.0.1:8000/tickets -Method POST -Headers $headers -ContentType "application/json" -Body $body
Invoke-RestMethod -Uri http://127.0.0.1:8000/tickets -Method GET -Headers $headers
```

**验收：** `POST` 返回 `ticket_id`，`GET` 列表出现工单；相同 `request_id` 不重复生成；`confirmed=false` 返回 400；缺少 `X-API-Key` 返回 401。

## 3. 将后端部署至 Render（关键步骤）
云端 Dify **不能**访问你的电脑 `http://127.0.0.1:8000`；必须使用可公网访问的 HTTPS API。

1. 在 GitHub 建一个名为 `staypilot-hotel-agent` 的仓库。
2. 在项目根目录用 `git init` 等命令上传代码，**不上传 `.env`、`.venv`、`.sqlite3` 或任何密钥**。
3. Render → **New → Web Service** → 选择 GitHub 项目。
4. **Root Directory** 选 `backend`（因为该文件夹里是 `app.py` 和 `requirements.txt`）。
5. **Language / Runtime** = Python 3。
6. **Build Command** = `pip install -r requirements.txt`。
7. **Start Command** = `uvicorn app:app --host 0.0.0.0 --port $PORT`。
8. **Environment** 新增 `STAYPILOT_API_KEY`，填相同格式的新随机密钥（可与本地不同）。
9. 选择适合的服务套餐；如当前仍有 Free 可用，可用于学习演示；检查最新价格和使用限制。
10. 部署成功后测试 `https://你的服务名.onrender.com/health`，返回 `{"ok":true,"demo":true}`。

**限制：** Render 免费实例在闲置时会休眠，并且 SQLite 本地磁盘数据在实例重启、休眠或重新部署后可能丢失。因此是模拟演示，不可当作持久业务数据库；如果需要持久存储，换 Postgres。Demo API 不包含完善的身份授权/租户隔离/限流，不要放真实客人信息，不要长期公开开放测试。

## 4. 在 Dify 添加模型
1. Dify 工作区 → **Integrations → Model Provider**（部分界面显示 Settings → Model Provider）。
2. 搜索/安装 DeepSeek 官方供应商插件，点击 **Setup**，输入 DeepSeek API Key。
3. 选择实际可用的聊天模型，先用一个简单测试验证模型能正常生成回答。
4. 如果后续需要向量检索，检查 Knowledge 的索引模型是否已配置。没有 Embedding 模型时，可使用当前界面允许的关键词/经济型索引或配置独立 Embedding 提供商。

不要将 DeepSeek Key 放在 Prompt、GitHub 或浏览器的 JS 中。

## 5. 配置酒店知识库
1. Dify → **Knowledge** → 创建知识库。
2. 导入 `knowledge/demo_hotel_policies.md`。
3. 选 **Classic Knowledge Base** 会更方便按本教程使用 **Classic Knowledge Retrieval** 节点；如果选新的 Agent Knowledge Base，后续必须用对应的 **Agent Knowledge Retrieval** 节点，不能混用。
4. 选择适合当前套餐与模型的索引模式。测试关键词“早餐时间 / breakfast”、“延迟退房 / late check-out”。
5. 确认查询能召回对应政策；如果检索不到，先解决索引/分段/模型问题，再添加 LLM 回答。

知识库政策是虚构酒店规则，不代表真实酒店的对外承诺。

## 6. 创建 Chatflow
Dify → Studio → Create App → **Chatflow**（不是简单 Chatbot，也不是独立 Workflow），命名为 `StayPilot Hotel AI Service`。

### 6.1 画出整体节点

```text
[User Input / Start]
   ↓
[Question Classifier]
   ├─ faq        → [Knowledge Retrieval] → [LLM: FAQ] → [Answer]
   ├─ service    → [Parameter Extractor] → [Code: Validate] → [If/Else]
   │                                                ├─ invalid → [Answer: 补充房号或描述]
   │                                                └─ valid   → [Human Input: Review]
   │                                                               ├─ Approve → [Code: Build Payload] → [HTTP POST] → [If/Else: HTTP status]
   │                                                               │                                         ├─ success → [Code: Parse] → [Answer]
   │                                                               │                                         └─ failed  → [Answer: 提交失败]
   │                                                               ├─ Reject  → [Answer: 已取消]
   │                                                               └─ Timeout → [Answer: 未确认，不提交]（如版本允许）
   ├─ complaint  → [Answer: 请联系前台/主管]
   ├─ emergency  → [Answer: 立即联系前台及当地紧急服务]
   └─ other      → [Answer: 请提供酒店相关问题]
```

### 6.2 Question Classifier
- 输入：User Input 的 `query`；有些旧版文档称 `sys.query`，用 UI 变量选择器选择实际存在的最新用户消息。
- 模型：你配置的 DeepSeek 聊天模型。
- 添加 5 个分类（**类别名**和说明分开填写）：

| Class | Description |
|---|---|
| `faq` | 查询酒店政策：早餐、入住、退房、Wi-Fi、停车；没有要求创建服务工单 |
| `service` | 请求送物品、维修空调/灯具/浴室设备等需要创建工单的非紧急事项 |
| `complaint` | 针对卫生、噪声、服务质量的投诉，需要人工受理而非默认自动赔偿 |
| `emergency` | 烟雾、火灾、重大漏水、紧急人身危险等；优先保障安全 |
| `other` | 不属于以上的请求，包括无关问题或含糊不清的内容 |

分类指导：紧急情况优先于普通维修；投诉优先由人工受理；不要在没有确认的情况下创建工单。

## 7. FAQ 分支：RAG
1. 在 `faq` 出口连 **Classic Knowledge Retrieval**，选择你建好的 Classic 知识库，查询变量用用户最新输入。
2. 再连一个 **LLM**。在 LLM 的 **Context** 位置绑定检索输出（不能只写在 Prompt 里却未绑定 Context）。
3. LLM System Prompt：

```text
你是星澜酒店（虚构）的 AI 服务助手。只依据检索到的酒店知识库回答政策问题。
如果知识库没有明确答案，直接说“当前资料中没有这项政策，请联系前台确认”。
不要虚构Wi-Fi密码、收费、空房情况、早餐包含情况或具体承诺。
按用户输入的语言回复；回答尽量简明。
如果用户要求提交工单，需走服务请求流程，不能在FAQ分支假装已提交。
```

4. LLM User Prompt 提供用户问题，确保引用到最新 query。
5. 连 **Answer** 节点，选择该 LLM 的 `text` 输出。
6. 试运行 `早餐几点？` 期望 `06:30–10:00`，`What time is breakfast?` 期望同样时间且英文答复；`Wi-Fi 密码是多少？` 不应编造密码。

## 8. Service 分支：自动理解→校验→确认→提交

### 8.1 Parameter Extractor
- 输入：用户最新 query；模型：DeepSeek。
- 定义以下参数；为了允许主动检测缺失，房号等字段在提取器中**不强制必填**，必填校验由后续 Code 节点负责。

| Field | Type | Description |
|---|---|---|
| `room_number` | String | 房号，如 1208，未提及时输出空或 null，禁止猜测 |
| `category` | String | 只能是 `housekeeping` 或 `maintenance` |
| `summary` | String | 服务请求简述，保留关键物品或故障信息 |
| `quantity` | Number | 物品数量；未提及通常为 1 |

Extraction instructions 示例：

```text
从用户提供的酒店服务需求中抽取结构化字段。不要猜测未提供的房号。
送水、毛巾、枕头：category=housekeeping；空调、灯具、浴室设备维修：category=maintenance。
如一句话包含多个相互独立的服务请求，当前MVP不能同时创建多个工单，应提示用户每次提交一项请求。
输出英文固定枚举，summary 保留用户实际诉求，不要添加虚构物品或数量。
```

### 8.2 Code：Validate Ticket
添加 **Code → Python**，从 `dify_snippets/validate_ticket.py` 复制 `main()` 函数。添加输入变量：`room_number`、`category`、`summary`、`quantity`，分别绑定 Parameter Extractor 输出。

添加输出：`valid` Boolean；`error` String；`room_number` String；`category` String；`summary` String；`quantity` Number；`preview` String。

用 If/Else 判断 `valid == true`。False → Answer，展示 Code 输出 `error` 并提示用户在**新消息中重新提交完整请求**。这样首版不会因缺失字段直接写入工单。若要逐项追问且记忆上下文，可在第二版增加 Conversation Variables/Variable Assigner。

### 8.3 Human Input：真实确认
在 `valid == true` 分支连 **Human Input**：
- Delivery Method：`Web App`。
- Form Content：`请检查并确认以下服务请求：` 然后插入 Code 节点 `preview` 变量（用变量选择器，而非手打占位符）。
- User Actions：`确认提交`（action ID 建议 `approve`）、`取消`（`reject`）。
- 如可配置 Timeout Branch：连到“不提交，超时取消”的 Answer；不能把超时当同意。
- **只有确认提交的出口才连接 HTTP POST**。取消/超时直接答复，不连 HTTP。

### 8.4 Code：Build Payload（仅在确认之后）
确认分支再接 **Code → Python**，从 `dify_snippets/build_payload_after_approval.py` 复制 `main()`。配置输入：
- `room_number`、`category`、`summary`、`quantity`：来自 Validate Code 标准化后的输出。
- `request_id`：来自系统 `sys.workflow_run_id`（通常在系统变量选择器中可见）。

输出字段 `payload_json`，类型 String。生成的 JSON 会包含 `confirmed: true`，**但该节点只位于审批通过分支**，保证没有确认时无法调用写接口。

### 8.5 HTTP Request：POST /tickets
- Method：`POST`
- URL：`https://你的服务名.onrender.com/tickets`
- Auth：API Key → Custom Header，name=`X-API-Key`，value=Render `STAYPILOT_API_KEY` 对应的值（建议使用 Dify Secret 环境变量）。
- Content-Type：`application/json`。
- Request Body：选择 `Raw Text`/JSON raw 模式，将 Build Payload 节点的 `payload_json` **变量**插入作为整个 body，避免手写 JSON 变量导致数字、转义、中文引号格式出错。
- 可设置 connect/read timeout 和 HTTP 失败分支；不要把接口请求失败当成功。

### 8.6 If/Else + Answer：根据实际响应给出结果
- 判断 HTTP 的 `status_code` 是否是 201（当前演示后端成功创建返回 201）。
- 成功时增加 Code，输入 `response_body` 绑定 HTTP `body`，代码：

```python
import json

def main(response_body):
    body = json.loads(response_body) if isinstance(response_body, str) else response_body
    return {"ticket_id": str(body.get("ticket_id", "")), "status": str(body.get("status", ""))}
```

- 在 Answer 中插入上一步输出的 `ticket_id`、`status` 变量。例如：“工单已提交成功。编号：[实际变量]，状态：[实际变量]。”
- 非 201、解析失败、网络错误：Answer“目前未能确认工单已创建，请联系前台或稍后重试”，绝不能凭 LLM 编出一个工单号。

## 9. Complaint / Emergency / Other
在各自分支使用 Answer 节点，不必调用模型。
- 投诉：`我可以提供反馈建议，但当前演示系统未接通真实前台。请联系酒店前台/值班主管处理。`
- 紧急：`如果存在火灾、烟雾或人身危险，请立即撤离危险区域，联系酒店前台及当地紧急服务；不要依赖本聊天助手。`
- Other：`我目前可以协助酒店政策咨询、客房送物和设施维修请求，请描述您的需求。`

## 13. 常见故障
- `ModuleNotFoundError`：没有在正确环境执行 `pip install -r requirements.txt`。
- `401 Invalid API key`：Render 与 Dify 中的 `STAYPILOT_API_KEY` 不一致。
- `422 Unprocessable Entity`：请求 body 中某个字段类型、房号、quantity 或 confirmed 不符合 schema；查看 FastAPI 返回的 details。
- Render 启动失败：Root Directory 应为 `backend`，Start Command 应为 `uvicorn app:app --host 0.0.0.0 --port $PORT`，且配置了 STAYPILOT_API_KEY。
- Dify HTTP 连不上 `localhost`：只能从你的电脑访问本地地址，改用部署后的 HTTPS URL。
- 知识检索为空：核查知识库是否完成索引、检索节点类型和 Knowledge 类型是否匹配、是否选对 query 变量。
- Human Input 不显示：检查是否使用发布的 Web App，Delivery Method 是否为 Web App，是否真的走到服务且 Valid 分支。
- 送水数量显示为字符串：Parameter Extractor 设置 number，Code 转为 int，发送 Build Payload 生成的整段 JSON。
- `/tickets` 重启后数据没了：免费 Render 的 SQLite 本地文件是临时数据，正式持久化用外部数据库。
